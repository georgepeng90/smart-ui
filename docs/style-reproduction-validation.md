# 参考风格分析与项目绘制程序复现验证流程

本流程说明如何从参考中归纳可执行规则，编写项目适用的 Python 程序，并通过 Krita 生成可编辑、可追溯且支持局部修改的组件。工具见[项目工具说明](project-tools.md)，程序接口见[绘制程序约定](drawing-programs.md)。

## 参考分析与规则记录

已有项目先 `project_context`，新项目先 `project_create`。用 `project_add_reference` 登记只读原图，`project_inspect_reference` 查看完整图、适用区域及取样色块。区域坐标相对整图；根据缩略图测量时传入 `coordinate_size`。

实际查看图片后，按参考中适用的维度分析用色、轮廓、描边、明暗与高光、材质、纹理、图标文字关系和尺寸变化规则。不必给每份参考套齐相同栏目；没有证据的特征不凭空添加。引用参考 ID 和区域，将可见观察、制作假设及待测参数区分开。

取样是原始 RGB 通道中位数、范围和透明度，没有 ICC 转换或背景合成。截图颜色是表观色，抗锯齿边缘、文字及遮挡可能造成混色。截图不能唯一证明原始笔刷、图层顺序、材质或光源数量。

用 `project_update_style` 保存有依据的规则与共用参数，由工具生成 `style.md`。共用参数可以是项目适用的色板、尺寸规则、笔刷或纹理参数，字段由项目程序定义；不能把历史按钮参数当作通用要求。独立 `reference-style` Skill 负责这项分析及文档维护。

## 项目程序与首个样片

按当前参考和目标制作可检查的程序，定义入口 `build(parameters, spec, component_id)`。用 `project_save_program` 保存，再用 `project_define_component` 通过 `spec.program_id` 关联程序。先 `project_plan_component` 检查可执行计划与几何约束，再确认 Krita 连接、查询精确笔刷并实际绘制。

程序保存只检查语法；计划阶段才运行源码。程序在独立 Python 进程运行，60 秒超时，属于可信本机代码，不是安全沙箱。图层数量、命名、分组、蒙版和绘制步骤应服务于编辑需求，不要求七层或任何固定角色。

原生路径或椭圆填色应如实描述为几何填色。查看实际 PNG 后，用指定运行与参考中无遮挡的区域做对照。

## 对照参考、记录偏差和复查

1. 用 `project_compare_component` 选择参考和运行预览的可比区域。先以原像素尺寸查看。需要调整展示尺度时，显式指定等比倍率，保留真实的轮廓比例。检查棋盘背景下的透明边缘，分析颜色时结合原图取样。可以用 `project_get_comparison` 重新查看同一份快照及反馈。
2. 查看拼图后，用 `project_record_feedback` 记录少量具体、可操作的偏差。把观察和建议分开，例如“参考两侧的暗边约为正面宽度的十分之一，产物暗边更窄”与“调整边缘节点的宽度参数”。有依据时关联计划节点 key 和风格规则 ID，按问题范围选择修改规格、程序或共用规则。
3. 执行修改，保存并检查新运行。再次对照同一原图区域，采用可比较的产物裁切和显示尺度。查看新拼图后用 `project_update_feedback` 逐条复查。可继续跟进、标记已修正，或写明不再跟进的理由。保留原始偏差和每次复查。绘制成功与技术检查通过本身不足以判定偏差已修正。

评估当前产物时，查看反馈摘要中的 `applies_to_current_run`。后续绘制可能使历史结论失去适用性，工具会保留原反馈状态，当前版本的结论需根据其对照复查。

提交评估时展示对照拼图、实际 PNG 和可编辑源文件，说明视觉判断依据及待确认项。反馈来源是记录者的声明，项目风格确认仍需要用户明确给出。

## 变体、局部修改与版本

按项目需要选择换色、尺寸、状态或材质变体验证。伸缩规则应明确哪些长度固定、哪些随尺寸变化、哪些需要重新构形；不要把整张 PNG 拉伸代替可编辑构建。验证应使用项目自己的规则，并检查变体是否符合这些规则。

局部修改先保留完整规格并更新必要字段，再生成新计划，以 `layers=[节点key]` 选择目标。目标可以是绘画图层、分组或透明度蒙版，工具比较上次计划，拒绝非目标变化；不限定为高光或某个字段。完整重画也要求当前结构和画布匹配，新尺寸或结构暂用新组件 ID。

选择分组只更新分组自身属性，不隐式更新子树；需要修改子节点时逐一列出它们的 key。没有旧 plan 的历史资产，应先完整绘制一次再使用局部更新。

规则或共用参数变化提升风格版本；程序源码更新产生程序版本，依赖组件需要重新检查。旧执行记录保留实际风格、程序及规格摘要。只改记录版本号或文档不能证明资产已经更新。

## 技术检查与视觉验收

`project.json` 是 schema 2 的唯一结构化数据源，`style.md`、`components.md` 为自动生成摘要，不手改。程序版本存于 `programs/<id>/<version>.py`。每次运行保留程序、计划、风格快照、实际操作、结果和成功产物，源文件固定为 `assets/<component_id>.kra`。

技术检查保存并重开文件，对比节点 UUID、层级、属性及像素摘要。局部更新额外检查非目标节点。Krita 根节点 UUID 不作为持久化依据。

| 验收维度 | 依据 |
| --- | --- |
| 技术正确性 | 源文件与证据存在，保存重开后节点和像素一致 |
| 局部修改 | 同一 .kra 中仅改变选定范围，非目标内容保持一致 |
| 参考接近程度 | 在明确裁切区域和显示尺度的对照中比较轮廓、用色、明暗、纹理和细节 |
| 变体一致性 | 变化遵守项目规定的共用关系与伸缩规则 |
| 可追溯性 | 产物对应实际程序源码、计划、参数、规格、精确笔刷与执行记录 |

`verified` 只代表技术检查通过。展示参考对照、实际 PNG 和 `.kra`，说明尚未获得的视觉确认；不能把模型评价或工具成功填成用户确认。

进入执行后的失败追加实际错误并保留现场，旧成功记录保留但不能证明当前磁盘文件有效。先检查运行目录、请求结果与 Krita 文档，不自动重发超时请求。若资产生成后项目 revision 冲突，保留产物并明确记录未更新。复现不足时说明偏差来自参考信息、规则、参数、程序或接口的哪一部分，不用底层批量笔触耗时代表完整复现效率。
