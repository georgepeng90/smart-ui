# 参考匹配与按需修正流程

本流程使用现有参考、组件对照、视觉检查和页面快照工具，由 Agent 判断偏差并按需修正。目标是缩短达到当前参考匹配要求所需的总时间，同时关注首次可查看产物的等待时间；不规定每个环节必须跑满几轮，不增加自动评分后端或逐步骤人工审批。工具见[项目工具说明](project-tools.md)，程序接口见[绘制程序约定](drawing-programs.md)。

这里的程序制作与保存重开检查适用于基础 UI。ICON（图标）图像通过宿主提供的生图或图像编辑能力制作，共享适用风格依据；SmartUI 登记当前图像资产并提供静态 UI 组合预览。分别检查图像本身和目标尺寸下的组合效果。SmartUI 不提供生图后端，不要求每张 ICON 对应 PhotoCraft 程序或可分层源文件。登记与组合操作见[项目工具说明](project-tools.md#独立图像资产与静态组合预览)和[ICON 资产 Skill](../skills/icon-assets/SKILL.md)。

## 参考分析与规则记录

已有项目先 `project_context`，新项目先 `project_create`。用 `project_add_reference` 登记只读原图，`project_inspect_reference` 查看完整图、适用区域及取样色块。区域坐标相对整图；根据缩略图测量时传入 `coordinate_size`。

实际查看图片后，按参考中适用的维度分析用色、轮廓、描边、明暗与高光、材质、纹理、ICON 与文字的关系和尺寸变化规则。注明规则适用于基础 UI、ICON 还是两者，伸缩约束与图像细节要求分别记录。不必给每份参考套齐相同栏目；没有证据的特征不凭空添加。引用参考 ID 和区域，将可见观察、制作假设及待测参数区分开。

先明确当前交付范围与少量决定观感的特征，区分需要匹配参考的部分和按业务要求调整的部分。分析随实际样片校准，不另加纯文字审查；若样片符合已写规则却仍偏离参考，应检查规则是否遗漏特征，而不是只改制作参数。

取样是原始 RGB 通道中位数、范围和透明度，没有 ICC 转换或背景合成。截图颜色是表观色，抗锯齿边缘、文字及遮挡可能造成混色。截图不能唯一证明原始笔刷、图层顺序、材质或光源数量。

用 `project_update_style` 保存有依据的规则与共用参数，由工具生成 `style.md`。共用参数可以是项目适用的色板、尺寸规则、笔刷或纹理参数，字段由项目程序定义。独立 `reference-style` Skill 负责这项分析及文档维护。

文字通过 `project_update_typography` 保存独立规范并生成 `typography.md`。按内容角色归纳固定字号，分别记录字体、行高、字距及填色、描边、投影的参数和依据。使用正式 Chromium 页面制作文字样片，检查实际尺寸、背景、复杂字形和长文案；静态简单组合不用于完整文字效果验收。方法与来源见[文字设计规范](typography-plan.md)。

## 代表组件与必要组合

先选覆盖主要画法及当前关键状态的少量代表组件，校准后再推广到整组。已有样片适用时直接复用，不为新任务重复建立相同校准。代表组件使用后续制作的同一程序和共用参数，避免验证一套画法、批量制作另一套。

定义程序入口 `build(parameters, spec, component_id)`，用 `project_save_program` 保存，再用 `project_define_component` 通过 `spec.program_id` 关联。首次编写或需要诊断计划时，用 `project_plan_component` 单独查看计划与几何约束；`project_draw_component` 本身也执行程序并严格预检，已明确的参数调整无需重复单独预检。实际制作前核对 PhotoCraft 版本。

程序保存只检查语法；预检和绘制入口都会在独立 Python 进程运行源码，60 秒超时，属于可信本机代码，不是安全沙箱。图层数量、命名、分组、蒙版和绘制步骤服务于编辑需求。

需要判断组件与图文的关系时，组合一个典型小区域，例如一条含面板、文字、图标和按钮的升级条目。优先复用已有组合；简单等比预览可用 `project_create_composition`，需要伸缩几何或文本框时用正式资产和页面布局工具。两种方法按需求选用，不重复制作两套检查。只加入本次必要内容，不为基础组件校准提前补齐完整页面、场景、全部图标、未来状态或 Unity 接入。占位范围需任务允许并明确标记，它不能证明完整美术效果，也不能成为误改基础组件的依据。

原生路径或椭圆填色应如实描述为几何填色。查看实际 PNG 后，用当前产物与参考中无遮挡的区域做对照。

## 对照参考、记录偏差和复查

1. 对代表组件或发现偏差的组件，用 `project_compare_component` 选择参考和当前组件预览的可比区域。优先按目标显示尺寸核对，按需要分别计算并显式指定参考与产物的等比倍率；两端工具默认倍率均为 1，不会自动对齐尺寸。指定纯色背景下的组件及状态比较可用 `project_create_visual_check`，无明暗诊断需求时显式传 `grayscale=false`；放大、透明边缘、多背景和其他尺寸检查按问题使用。已有同条件对照或检查用对应读取工具复用，不重绘、不重复生成。
2. 查看拼图后，用 `project_record_feedback` 分开记录可见现象和建议改动，例如“产物暗边比参考窄”与“调整边缘节点宽度”。优先处理目标尺寸可见、重复出现或明显影响整体观感的偏差，有依据时关联计划节点 key 和风格规则 ID。先收拢问题，按原因集中修改规格、程序或共用规则；不每发现一项就重绘，也不凭“更精致”等笼统评价继续迭代。
3. 保存修改并检查新运行，以同一参考区域、可比裁切和显示条件复查产物，确认目标偏差改善且受影响状态或组合没有退步。更新对照，再以当前 `comparison_id` 调用 `project_update_feedback` 逐条复查。需要对比已提交的旧产物时从 Git 查看。技术检查与视觉复查分别判断。

评估当前产物时，核对反馈所依据的对照和实际组件产物。后续绘制后按需要重新对照。

提交评估时展示对照拼图、实际 PNG 和可编辑源文件，说明视觉判断依据及待确认项。反馈来源是记录者的声明，项目风格确认仍需要用户明确给出。

## 继续修正与结束条件

参考分析、代表组件和页面是三个检查位置，不是三套固定修正循环。没有明确偏差就不重绘；继续修正需要有参考依据的可见问题和可执行改法。整组制作后检查共用关系及异常项，不给每个相似组件重复全套审查。不能用单一相似度分数代替这些判断。

当前交付范围内的主要参考特征已匹配、已处理偏差完成复查且相关状态没有退步时，可以结束模型自审。参考信息不足、没有可信改法、连续修正没有明显收益或达到已有的时间及成本约定时，停止重复尝试，说明剩余差异和原因，必要时重新检查分析或制作方法。停止不等于通过，未解决反馈保持开放，不能仅为结束流程标为 `resolved` 或 `dismissed`；用户确认仍单独记录。

独立审阅用于判断有分歧、修正停滞或确有必要的关键检查，不为每个组件默认安排串行审阅。审阅者先看当前要求、原始参考及实际产物，再按需要读取制作说明；复用已有图片与记录，不重新制作一套。

## 页面对照与反馈

完整页面对照在实际页面制作时进行。先读取已有构建，核对布局和实际使用的资产是否符合本轮目标。布局或资产更新后显式重建受影响页面，再复查页面效果。

将参考可比区域或整页与页面 PNG 按可比显示尺度查看，先看视觉重心、明暗面积、疏密及图文比例，再区分布局、文字、导出伸缩和源资产问题。尊重当前业务内容与布局要求，不为逐像素相同改变业务语义。汇总同源偏差后集中修改相关定义或资产，构建一次，再查看整页和受影响区域；无变化时用 `project_get_page_build` 复查快照，不重新构建。

现有 `project_record_feedback` 和 `project_update_feedback` 绑定组件参考对照，不接受页面构建 ID。页面及组合观察沿用业务项目现有非受管工作记录，简短记录参考 ID 与区域、构建或组合 ID、实际资产及其摘要、偏差、改法及复查结果；不为每轮另建长报告，不手改项目状态或受管 Markdown。问题定位到源组件后，用组件对照及反馈工具跟进。页面修改方法见 [page-composition Skill](../skills/page-composition/SKILL.md)。

## 变体与局部修改

按项目需要选择换色、尺寸、状态或材质变体验证。伸缩规则应明确哪些长度固定、哪些随尺寸变化、哪些需要重新构形；不要把整张 PNG 拉伸代替可编辑构建。验证应使用项目自己的规则，并检查变体是否符合这些规则。

局部修改先保留完整规格并更新必要字段，再生成新计划，以 `layers=[节点key]` 选择目标。目标可以是形状、像素图层或分组；蒙版属于像素或分组节点的属性，随所属节点更新。工具比较上次计划，拒绝非目标变化；不限定为高光或某个字段。完整重画也要求当前结构和画布匹配，新尺寸或结构暂用新组件 ID。

选择分组只更新分组自身属性，不隐式更新子树；需要修改子节点时逐一列出它们的 key。局部更新使用已登记的当前计划及其摘要，供工具校验和比较。

规则、共用参数或程序变化后，核对依赖组件当前产物的风格、源码及规格摘要，按实际影响重绘和复查。

局部更新仍会保存完整文件、渲染整图并重开验证，应收拢明确偏差后执行。根据实际影响选择本次允许修改的节点，不因关联变化或校验失败自行扩大任务范围。保留项目 revision 和源文件摘要校验、保存重开与未选内容检查；减少重复执行不能变成省略必要校验。

## 耗时与简短记录

评估流程效率时，沿用项目现有工作记录，记录首次可查看产物的等待时间、达到本轮参考匹配要求的总时间、修正次数及解决的主要偏差。按实际发生的阶段区分模型分析与程序修改、工具执行、看图复查；并行阶段不简单相加为总耗时，未完成匹配时记录当前已耗时间及未完成状态。时间来自实际起止记录，无法测得就注明，不能估填成实测。

当前 `drawing_elapsed_ms` 包含后端检查、会话、原生执行、保存渲染、重开和技术验证，不覆盖前置程序执行、最终发布、对照、页面构建及模型判断；它不能代表整轮耗时。日常审查优先读取当前摘要、关键图片和开放问题，按需展开详情。这是使用现有工具的工作方法，尚无自动汇总整轮耗时或自动判断修正收益的接口；真实任务的质量与耗时收益仍需验证。

## 技术检查与视觉验收

`project_root` 是业务工程根目录的绝对路径。提交 `smart-ui/` 中的当前项目资料。目录与协作规则见[工程目录与持久化路径](project-tools.md#工程目录与持久化路径)。诊断和缓存留在本机 `.smartui/`，历史资料通过 Git 查阅。

技术检查保存并重开文件，对比原生节点 ID、层级、属性及像素摘要。局部更新额外检查非目标节点。

| 验收维度 | 依据 |
| --- | --- |
| 技术正确性 | 源文件与证据存在，保存重开后节点和像素一致 |
| 局部修改 | 同一 .pcraft 中仅改变选定范围，非目标内容保持一致 |
| 参考接近程度 | 在明确裁切区域和显示尺度的对照中比较轮廓、用色、明暗、纹理和细节 |
| 变体一致性 | 变化遵守项目规定的共用关系与伸缩规则 |
| 可追溯性 | 当前产物对应实际计划、输入摘要、后端构建和检查结果 |

`verified` 只代表技术检查通过。展示参考对照、实际 PNG 和 `.pcraft`，说明尚未获得的视觉确认；不能把模型评价或工具成功填成用户确认。

制作执行失败时先检查 `.smartui/` 中的诊断、请求结果与 PhotoCraft 文档，再决定如何处理。发布前发生项目 revision 或源文件摘要冲突时，拒绝覆盖源文件。复现不足时说明偏差来自参考信息、规则、参数、程序或接口的哪一部分，不以单次底层操作耗时代替整条制作流程耗时。
